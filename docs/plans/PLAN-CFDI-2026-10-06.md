# CFDI individual: integración y operación

## Decisión y alcance

Se integra Facturapi v2 después de comparar documentación oficial de Facturapi,
Facturama y SW. La [investigación](../research/CFDI-PROVIDER-DECISION-2026-10-06.md)
contiene fuentes, precios consultados y limitaciones documentales. La API del
proveedor certifica mediante un PAC; Kova no se presenta como certificador.

Este release implementa facturas individuales CFDI 4.0 de ingreso, MXN, PUE,
para ventas pagadas, con clasificación explícita IVA 16%, 8%, 0%, exento o sin
objeto. No timbra globales, complementos de pago, notas de crédito, IEPS o
retenciones. No cambia impuestos ni importes de tickets históricos.

## Activación por el dueño del negocio

1. Crear una cuenta en [Facturapi](https://www.facturapi.io/) y una organización
   para el RFC emisor. Revisar la contratación API y sus costos vigentes.
2. Configurar datos fiscales, CSD y Carta Manifiesto directamente en el portal
   del proveedor. Kova no recibe archivos de e.firma ni llaves del CSD.
3. En Integraciones de Kova, guardar el emisor y conectar primero la llave
   **Test de la organización**. No usar una User Key administrativa.
4. Registrar una solicitud desde una venta pagada, revisar el receptor y mapear
   cada concepto a su clave SAT, unidad e impuesto correcto. La vista previa
   debe conciliar con el cobro. Emitir, consultar estado y descargar XML/PDF.
   Todos los documentos Test carecen de validez fiscal.
5. Tras verificar el flujo con credenciales reales de prueba, conectar la llave
   Live. Kova verifica la organización, RFC y certificados antes de una emisión.
   El primer timbrado productivo debe corresponder a una venta real autorizada.

Las credenciales se ingresan únicamente en el campo protegido de Integraciones.
No enviarlas por chat, incorporarlas al repositorio ni ponerlas en el frontend.
El host conserva una llave de cifrado estable; el despliegue sólo crea esa llave
si no existe. Su rotación requiere un procedimiento separado de recifrado.

## Recuperación y evidencia

El intento y su payload quedan confirmados en PostgreSQL antes del POST externo.
Un timeout o error ambiguo conserva la reserva de la venta. Consultar el mismo
documento permite reconciliar por ID o referencia externa; una búsqueda vacía no
autoriza a emitir otro documento. Sólo el XML validado permite confirmar emisión.

Solicitar cancelación no significa que el SAT haya cancelado. La venta continúa
reservada hasta confirmación del proveedor; entonces Kova registra la reapertura
fiscal. Con CFDI Live vigente o incierto se bloquean devoluciones/anulaciones y
nuevas inclusiones en borradores globales. Los documentos Test no afectan ese
registro fiscal.

La exportación de cuenta incluye metadatos públicos y XML persistidos, excluye
credenciales y conserva aislamiento por negocio. Eliminar la cuenta de Kova no
cancela CFDI ante el SAT; descargar la evidencia antes de su eliminación.

## Validación del release

Se requieren pruebas HTTP de emisión/reconciliación/cancelación, errores
ambiguos, exactitud decimal, receptor corregido y discrepancias XML; aislamiento
tenant/sucursal, RBAC y grants con rol de aplicación; concurrencia PostgreSQL
entre emisión y cierre global; portabilidad y eliminación de cuenta; migración
0074 con datos previos y negativa de downgrade destructivo; frontend y E2E
dev/preview. CI publica el mismo SHA en Fly y Vercel y verifica su aceptación.

Sin cuenta ni credenciales del proveedor no se considera verificado un timbrado
real sandbox o SAT. Los dobles de prueba verifican comportamiento de Kova, no
sustituyen esa evidencia externa.
