# Kova POS — UX / Product Review

**Date:** 2026-05-19
**Reviewer persona:** Senior PO + UX reviewer evaluating as a prospective Mexican SMB owner deciding whether to pay the $199 MXN/month subscription.
**Method:** Live walkthrough of `https://point-of-sale-ochre.vercel.app/` (Edge + Claude in Chrome, signed in as `posprojectsupport@gmail.com`) plus code-level review of the `frontend/` source. Mobile responsive evaluated against the responsive CSS in source (live resize did not register in the test browser; findings cross-checked against media queries in `routes/Home.tsx` and Tailwind breakpoints in app views).
**Scope:** Visual layer + UX only, per `CLAUDE.md`. No backend logic changes proposed.

---

## A. Overall diagnosis

### Is this app ready to sell?
**Almost, not yet.** The landing page is genuinely premium and would convert a curious owner to click "Empezar gratis." The signed-in product is solid mechanically (POS, shifts, offline, inventory, reports, Spanish-first) and that's a real differentiator vs. the typical Mexican POS competition. But the **first 60 seconds inside the app actively damage the value perception** for a fresh account, and the **setup is bumpy where it has to be smooth** (logo upload, locale/timezone fields, "QA Concha" demo data, free-text settings inputs). A prospect on trial day 1 sees red "−100% vs ayer" KPIs, a destructive banner at the top of every screen, and a settings screen that asks them to paste a "Logo del recibo (URL segura)" — that combination is enough for a non-technical owner to close the tab.

### Premium feel
**Landing: 8/10.** Stripe / Linear-tier composition. Hairlines, typography, dual-theme, interactive POS preview, "tres nodos · un circuito" narrative. This is a strong first impression.
**Authenticated app: 6/10.** Same brand tokens, same DM Sans, sidebar in Kova ink — but the polish drops noticeably. Spelling regressions (`senales`, `Todavia`, `aparecera aqui`, `dias`), accidental "QA Concha 20260512" demo data in a real account, an "Idioma" field that's a text input, and the dashboard "−100%" red badges all read as beta / unfinished.

### Value-prop clarity
The landing communicates value well ("Ventas, inventario y pagos orquestados desde un solo lugar — incluso sin internet"). The authenticated app does **not** continue that story. After login you're greeted with what looks like a paywall, not with proof of value. The dashboard's `BusinessHealthCard` + `InsightStrip` components in the source (`dashboard/BusinessHealthCard.tsx`, `dashboard/InsightStrip.tsx`) are the right idea but produce no useful narrative when the account has zero sales, which is the **exact state every paying customer is in for their first hour**.

### Conversion + retention likelihood
**Conversion to trial click:** High. The pricing card is bold, single-plan, no asterisks. "Sin tarjeta para empezar" removes the biggest friction.
**Activation (first real sale):** Medium-low. The setup checklist is good (3/7 step UI on dashboard), but logo upload, free-text timezone, and tiny demo products in the catalog will lose ~20–30% of trials before they record a real sale.
**Trial → paid:** Medium. The trial-expired billing page is well composed ("Lo que conservas al activar") but it has to compete against the negative first-touch experience above. If we fix items #1–#7 below, conversion to paid should jump meaningfully.

## B. Prioritized issue list

Each item is tagged `Critical` (blocks payment / trust / core use), `High` (degrades perceived value or usability), `Medium` (real issue but non-blocking), or `Low` (polish).

### CRITICAL

1. **CRITICAL — Logo "upload" is a URL paste field.** `settings/SettingsView.tsx:184` renders `Field label={copy.settings.logoUrl}` for `receipt.logo_url` as a plain text input. There is no upload, no preview, no drag-and-drop, no image cropper. CLAUDE.md explicitly calls out logo configuration as a core setup task; the landing page lists "Logo y personalización del POS" as a paid feature. Asking a tortillería owner to host an image to get a URL is a deal-breaker.

2. **CRITICAL — Dashboard greets new accounts with red "−100% vs ayer" KPIs.** `dashboard/DashboardView.tsx:75` `DeltaBadge` falls through to the `pct < -0.5` branch and renders `TrendingDown` in `text-destructive` whenever previous > 0 and current == 0. On the live `posprojectsupport@gmail.com` account, all four KPIs (Ventas netas, Órdenes, Ticket promedio, Devoluciones) render `↘ 100% vs ayer` in red. That is the **first thing a paying customer sees**. For a fresh / low-activity account this is misinformation, not insight.

3. **CRITICAL — Persistent red "Facturación requerida" billing banner pins to every screen.** `layout/AppShell.tsx:201` mounts `<BillingBanner />` above `<Outlet />`, so it appears on Dashboard, Caja, Catálogo, Inventario, Reportes, Configuración and Facturación itself (where it's redundant with the page body's own warning). On the test account it occupies ~80px on every view and uses destructive color, hijacking attention away from the actual work. This is correct behavior when truly expired, but it should never appear *during* the active trial, and it should never appear duplicated on the billing page itself.

4. **CRITICAL — "QA Concha 20260512" demo product shipped in the seed.** The signed-in account ships with `Dona` and `QA Concha 20260512 / QA-CON-20260512` visible in `/register` and `/catalog`. This is dev/test scaffolding leaking into the customer's real catalog. Looks deeply unprofessional; suggests "we forgot to clean up."

### HIGH

5. **HIGH — Spanish accent errors throughout `i18n/messages.ts`.** Confirmed in source: `senales` (lines 571, 603), `Todavia` (605, 610), `aparecera aqui` (613), `dias` (550, 605), `cancelacion` (592), `senal` (603). Every one of these is visible to the user in the Reports view. For a product whose tagline is *"Hecho en México · es-MX"*, this is credibility damage.

6. **HIGH — Setup screen uses free-text inputs for Idioma / Moneda / Zona horaria.** `settings/SettingsView.tsx:169–171`. The user must type `es-MX`, `MXN`, `America/Mexico_City` exactly. There is no validation, no dropdown, no help text. A real owner will type "Mexico" and hit save and not understand why something later breaks. These should be a `<Select>` with sensible defaults already pre-filled (which they are, technically — so the field could just be a read-only display + "Cambiar" link for the rare case).

7. **HIGH — Trial countdown / "what changes when it expires" is missing during the active trial.** The dashboard surfaces the onboarding checklist and KPIs, but never the **trial days remaining** or **what concretely happens when the trial ends**. The "Lo que conservas al activar" panel on `/settings/billing` is excellent but only seen *after* expiration. Show that value preview during the trial.

8. **HIGH — Settings has no logo preview, no business-name preview, no "this is how your recibo will look" panel.** A receipt-printer business needs to *see* what the receipt looks like before they trust their first sale to it. Right now you configure invisible fields and hope.

9. **HIGH — Empty states on Reports tell the user "no hay datos" 9 different ways with no path to fix it.** Every section says some variation of "Sin ventas / Sin pagos / Sin senales / Sin datos." There's a single "Acciones recomendadas → Genera la primera venta del periodo" at the very bottom. That recommendation should be a primary CTA at the top of the page when the account has zero qualifying sales — not the page's footer.

10. **HIGH — Sidebar tenant name is rendered raw (`TESTING` in all caps).** `layout/AppShell.tsx:101` shows `state.tenantName` with no normalization. The test account is literally called `TESTING`, but real customers can sign up as "café lupita" or "CAFÉ LUPITA" and we render it verbatim in the brand area, fighting the carefully designed Kova mark above it. Apply a presentation transform (title case, length truncation, never all-caps) or render it in the same uppercase-tracking style as the `kova` chip.

### MEDIUM

11. **MEDIUM — Dashboard `Mezcla de pagos` + `Productos top` are zero-state cards that take up half the page.** `dashboard/DashboardView.tsx:432–512`. When there are no sales, two large cards just say "Sin pagos hoy" and "Sin ventas hoy." Collapse, hide, or replace with a "Cómo se llena este panel" explainer that doubles as an education moment.

12. **MEDIUM — Landing hero pricing label is rendered from JS constants but no visible "$199 MXN / mes" appears until you scroll all the way to the pricing section.** The hero only says "Empezar gratis" and "Ver el POS en vivo." Owners scanning will not know the price unless they scroll. A trust-builder line like "Plan único · $199 MXN/mes · sin comisión por venta" near the hero CTAs would qualify the lead faster.

13. **MEDIUM — Dashboard KPI cards show `sub` text "100% vs ayer" both in absolute terms and a `↘` icon — but no period label.** When the user filters by "Mes" in Reports the comparison semantics change. The same `vsYesterday` literal is reused across contexts. Make the comparison label dynamic ("vs. ayer", "vs. semana pasada", "vs. mes pasado").

14. **MEDIUM — POS register cart shows `Pago dividido` checkbox before the user has picked a payment method.** This is a "power user" toggle that adds cognitive load on first sale. Hide it under an "Opciones avanzadas" disclosure until the user has at least one payment method selected.

15. **MEDIUM — `Empleados` invite UX uses a native `<select>` element with default browser styling** (`settings/SettingsView.tsx:200`). Inconsistent with the otherwise polished form. Use the existing styled `Select` primitive (or shadcn `Select`) for visual consistency.

16. **MEDIUM — Landing rendering issue at large viewports.** On a 1568×682 Edge window the dark hero section ends with a vertical seam and a strip of white to the right (visible in the captured live screenshots). The `.lp-root { max-width: 100%; overflow-x: clip; }` rule in `routes/Home.tsx:1024` is meant to prevent this but the parent layout doesn't have `width: 100%`/`min-width: 100%` set, so the section background doesn't fully paint. Verify and add `min-width: 100vw` or set the body bg to `--page-bg`.

17. **MEDIUM — Onboarding checklist is buried below the trial banner and dashboard header.** `dashboard/DashboardView.tsx:329` renders `<OnboardingChecklist />` *after* the greeting block. For an account at 3/7 the checklist is the single most important UI element on the page; promote it above the KPI grid until `allDone === true`.

### LOW

18. **LOW — Inconsistent CTA verbs.** Landing uses "Empezar gratis," sidebar shows "Ir al dashboard," nav has "Crear cuenta," login button says "Iniciar sesión." All fine individually but "Empezar gratis" and "Ver el POS en vivo →" use different chevron styles (SVG arrow vs. text arrow).

19. **LOW — Dashboard greeting `Buenos días` is hardcoded by `getGreeting()`.** Should be time-zone aware against the tenant's `timezone` field, not the browser.

20. **LOW — Sidebar bottom shows the user's email + `Propietario` label.** For a single-user account that's fine, but for a multi-cashier account the cashier is going to see `Propietario` until you also wire up the role label correctly. Confirm `roleLabel()` is being passed the right role.

21. **LOW — `Acciones rápidas` cards are duplicates of the sidebar nav.** Consider replacing with *contextual* actions ("Cerrar turno", "Imprimir Z del día", "Exportar ventas") that aren't already one click away.

22. **LOW — Reports date pickers default to today/today (`05/19/2026 → 05/19/2026`).** For "Hoy" that's correct, but the inputs accept type-in dates with no format help. Add `placeholder="DD/MM/AAAA"` and an inline format hint, or use a proper styled date-range picker.

23. **LOW — Theme toggle in landing nav stores choice in `localStorage` (`kova-landing-theme`)** but the authenticated app has no theme toggle and is always light. Either bring dark mode into the app or remove the landing toggle for now to avoid a broken promise.

24. **LOW — Hardcoded fragment of empty `<div>` in landing nav** (`routes/Home.tsx:276–277`): an opening "pill" wrapper renders with no children. Remove or fill.

25. **LOW — Footer links in landing all `href="#"`.** Producto / Soluciones / Compañía / Recursos columns are visually convincing but every link is a dead `#`. Either link real pages or replace columns with a single email/contact card.

## C. Actionable recommendations

For each Critical / High issue, the change, the rationale, the file(s), and acceptance criteria.

### Issue 1 — Logo upload (Critical)
**Change.** Replace the URL text input with a proper image upload: drag-and-drop zone + file picker, client-side preview, max 2 MB, accepted formats PNG/SVG/JPG, and a "Quitar logo" affordance.
**Why.** Logo is the #1 personalization that converts "POS" into "my business's POS." Asking owners to paste URLs is unreasonable for the target audience.
**Files.** `frontend/src/settings/SettingsView.tsx` (UI), `frontend/src/settings/api.ts` (multipart endpoint), backend storage of the binary (out of scope per CLAUDE.md visual-only rule — coordinate with backend owner).
**Acceptance.** Owner can upload a logo from their phone or desktop; sees the logo preview immediately; the logo renders inside `LogoMark` on receipts and (optionally) replaces the Kova mark in the sidebar.

### Issue 2 — Misleading dashboard deltas (Critical)
**Change.** Suppress `DeltaBadge` red downward badges when (a) current period has zero qualifying events AND (b) the tenant has fewer than 7 cumulative days of sales history. Show a neutral, copy-driven "Aún sin comparación" line instead. Add a unit test.
**Why.** Brand-new accounts will always be at "0 vs whatever," and we want the first-day vibe to be "let's get started," not "you're down 100%."
**Files.** `frontend/src/dashboard/DashboardView.tsx` (`DeltaBadge`), `frontend/src/i18n/messages.ts` (new copy `deltaWarmingUp`).
**Acceptance.** A fresh account with $0 today and any historical value renders neutral muted text "Aún sin comparación", not red "-100%." Test: spin up a tenant with 1 historical sale yesterday → today shows neutral, not red.

### Issue 3 — Persistent billing banner (Critical)
**Change.** Hide `BillingBanner` on `/settings/billing` (duplicate UI). During active trial, render as a soft, accent-colored info chip ("Te quedan X días de prueba — Revisar plan") not destructive. Only switch to red after grace period elapses. Allow dismissal for 24 hours via `localStorage`.
**Why.** A red banner on every screen feels like a Windows error, not a SaaS dashboard.
**Files.** `frontend/src/billing/BillingBanner.tsx`, `frontend/src/layout/AppShell.tsx`.
**Acceptance.** During trial: blue info chip with day-count, dismissible. Expired: red destructive (current behavior). On `/settings/billing`: not rendered at all.

### Issue 4 — Demo data in production (Critical)
**Change.** Audit the tenant-seed / signup path; remove any "QA Concha", `Dona`, `QA-CON-...` rows from the default catalog. Replace with **zero products** plus a strong empty-state ("Agrega tu primer producto" with a single primary CTA).
**Why.** Real customers see test/QA data → they assume the product is unfinished.
**Files.** Backend signup/seed (coordinate); `frontend/src/catalog/CatalogView.tsx` empty state.
**Acceptance.** New tenant created → 0 products in catalog, prominent illustrated empty state, "Agregar producto" CTA front-and-center.

### Issue 5 — Spanish accent errors (High)
**Change.** Fix `i18n/messages.ts`: `senales→señales`, `Todavia→Todavía`, `aparecera→aparecerá`, `aqui→aquí`, `dias→días`, `cancelacion→cancelación`, `senal→señal`. Add a lint rule (`eslint-plugin-spell` or a custom regex CI check) preventing common unaccented forms from being committed.
**Why.** For a product positioned as Mexican-first, missing accents read as "made by gringos" or "shipped in a hurry."
**Files.** `frontend/src/i18n/messages.ts` (lines 550, 571, 592, 603, 605, 610, 613), CI config.
**Acceptance.** No instances of those unaccented forms remain in `i18n/`; CI fails if a PR introduces one.

### Issue 6 — Free-text Idioma/Moneda/Zona horaria (High)
**Change.** Replace `Field` text inputs at `settings/SettingsView.tsx:169–171` with the existing styled `<Select>` primitive. Options: `Idioma: [es-MX]` (single for now), `Moneda: [MXN, USD]`, `Zona horaria: [America/Mexico_City, America/Tijuana, America/Cancun, America/Monterrey, ...]`. Default-fill them and hide inside an "Avanzado" disclosure.
**Why.** Free-text settings break silently when a non-technical user types the wrong string.
**Files.** `frontend/src/settings/SettingsView.tsx`, new const file for timezone list.
**Acceptance.** No way to save an invalid locale/currency/timezone. Defaults visible without user action.

### Issue 7 — Trial visibility during active trial (High)
**Change.** Add a `<TrialChip>` to the AppShell header (mobile + desktop) showing "Prueba · 12 días restantes" with the same blue accent treatment used in the landing pricing card. Click → `/settings/billing`. While trial is active, dashboard renders a small "Conserva esto al activar:" inline list near the onboarding checklist.
**Why.** Most paid conversions happen because the user sees the countdown and the explicit "what will I lose." Showing it only post-expiry trains users to think "well, I had nothing to lose."
**Files.** `frontend/src/layout/AppShell.tsx`, new `frontend/src/billing/TrialChip.tsx`.
**Acceptance.** During trial, day count visible at all times. Post-expiry, replaced by the existing destructive banner.

### Issue 8 — Receipt preview (High)
**Change.** Add a live receipt preview panel next to the `Ajustes del recibo` form. Updates as user types business name, footer, tax text. Shows mock data ("Café Lupita · 2026-05-19 22:13 · 1× Latte 12 oz · Total $52.00").
**Why.** Owners need to *see* their receipt before they trust their business to it.
**Files.** `frontend/src/settings/SettingsView.tsx`, new `frontend/src/settings/ReceiptPreview.tsx`.
**Acceptance.** Typing in any of the receipt-settings fields updates the visible mock receipt in <100ms.

### Issue 9 — Reports "all empty" state needs a primary action at the top (High)
**Change.** When `summary.order_count === 0` for the selected range, hide the 9 individual empty cards. Show one full-width hero card: "Sin ventas en este rango — Abre caja y registra una venta para que este reporte cobre vida" with a primary CTA to `/register` and a secondary "Cambiar rango." Show the empty data sections only after the first qualifying sale exists.
**Why.** Current state is 9 simultaneous "no data" cards, which actively communicates "the product doesn't work yet."
**Files.** `frontend/src/reports/ReportsView.tsx`.
**Acceptance.** Account with zero sales sees one consolidated empty state, not nine fragments.

### Issue 10 — Tenant name presentation (High)
**Change.** Apply a presentation transform when rendering `tenantName`: trim, truncate to 24 chars with ellipsis, sentence-case if all-caps or all-lower. Add a 32-char hard limit on the signup form.
**Files.** `frontend/src/layout/AppShell.tsx:101,197`, new `frontend/src/lib/formatTenantName.ts`.
**Acceptance.** "TESTING" renders "Testing"; "café lupita" renders "Café Lupita"; "ESTABLECIMIENTO MUY LARGO QUE NO CABE" truncates with `…`.

## E. Reports — KPIs that matter for an SMB POS

Drop or downgrade anything that doesn't lead to an action. The current Reports page is generous (executive summary, period sidebar, ventas-por-hora, ventas-por-bloque, devoluciones, desempeño por empleado, productos, métodos de pago) but the **storytelling** is missing. Replace "show every number" with "tell me what I should do this week."

**Tier 1 — Always visible (the daily briefing):**
- **Ventas del día / semana / mes** with comparison to same window prior period
- **Hora pico hoy vs. tu hora pico habitual** ("Hoy tu pico fue 13:00 — habitualmente es 14:00. ¿Algo cambió?")
- **Ticket promedio** with 7-day sparkline trend
- **Mezcla de pagos** (% efectivo / transferencia / tarjeta) — surfaces fee opportunities and cash risk

**Tier 2 — On the Reports page (the weekly review):**
- **Top 5 productos por margen** (not just by units sold) — requires `cost` field if not present; revenue-first if no margin data
- **Productos zombies**: en catálogo pero sin venta en X días — drives catalog cleanup
- **Días/horas muertos en la semana**: ventana donde la caja estuvo abierta sin ventas — drives staffing decisions
- **Empleados con mejor ticket promedio** (not just total ventas — that confuses with shift length)
- **% de descuentos / cortesías** del total — surfaces leakage
- **Conteo de devoluciones + razón principal** — surfaces product or process issues
- **Stock crítico que cruza umbral hoy** — actionable, not just informational

**Tier 3 — Insights, not metrics (the strategic narrative):**
- "Tu lunes baja 30 % vs. el resto de la semana. ¿Promoción de lunes?"
- "El 70 % de tus ventas son entre 13:00 y 15:00. Programa más personal en ese bloque."
- "Concha y latte se venden juntos el 40 % de las veces. ¿Combo?"
- "Sin ventas de las 19:00–21:00 los miércoles. ¿Cerrar antes?"

**Cut from default view:**
- The 9 simultaneous "Sin datos" cards (consolidate into one)
- Standalone "Zona horaria · America/Mexico_City" card on the period sidebar (move to settings)
- The dashboard `Devoluciones` KPI when count is 0 *and* there have never been refunds for this tenant

## F. Mobile & responsive

Code review of breakpoints (`routes/Home.tsx` 900/640/360, Tailwind `sm:/md:/lg:/xl:` across views) shows the responsive structure is in place. Specific concerns:

- **Landing.** `routes/Home.tsx:1069` collapses hero correctly at 640px and shrinks the headline at 360px — looks structurally fine. Verify the visible white-strip overflow at large widths (issue #16) doesn't repeat at 320px iPhone SE.
- **AppShell.** `layout/AppShell.tsx:206–237` has a 4-cell bottom nav (Register / Orders / Dashboard / Más) with safe-area inset padding. Good. But the **billing banner consumes the same vertical space on mobile as on desktop**; on a 667px-tall phone, ~80px of red banner + ~56px header + ~56px bottom nav leaves ~475px of usable canvas — combined with the persistent banner this is painful.
- **Register / Caja.** `register/RegisterView.tsx:430` uses `lg:grid-cols-[1fr_400px]` so the cart drawer collapses below the catalog on mobile — correct. There's a fixed `bottom-14` floating bar (`:1059`) which on top of the bottom nav (h-14) means the cart sits ~112px from the bottom of the viewport. That's fine, but verify there's no overlap when the keyboard is open during quantity input.
- **Catalog.** `catalog/CatalogView.tsx:147` collapses to single column at <`sm`. Good.
- **Reports.** `reports/ReportsView.tsx:317` uses `sm:grid-cols-2 xl:grid-cols-4` for KPIs — at 375px you get 1 KPI per row, which means 4 KPIs takes 4 screens. Consider `grid-cols-2` for small screens (compact cards) and only stack at very small.
- **Settings.** `settings/SettingsView.tsx:165` uses `sm:grid-cols-2`. At 375px the form is single-column, which is correct. But the page is one long scroll with no tabs — on mobile users may scroll past the section they need. Sprint 3 `S3-03` (tabbed sections) helps mobile most.

**Open verification (couldn't test live):** Live `resize_window` did not actually shrink the Edge viewport, so I could not visually confirm 375px behavior end-to-end. Recommended: run real device test on a mid-range Android (Samsung A14, Moto G) before sprint 3 sign-off.

## G. Ideal first-time experience (the north star)

What it should feel like when a new owner signs up at 9:00am Tuesday.

**9:00.** Owner lands on the Kova homepage from a WhatsApp share. Dark hero, "Tu negocio, en flujo constante" — they instantly get it: this is a POS for businesses like theirs. The interactive POS preview in the hero invites a click. Pricing is clearly $199 MXN/mes from the second screen.

**9:02.** They click "Empezar gratis." No credit card. They enter business name "Café Lupita," email, password. Verification token + magic-link arrives in 5 seconds (during dev mode, shown inline).

**9:03.** They land in the dashboard. Header reads *"Buenos días, Café Lupita"* (sentence case, transformed). Below that, the **onboarding checklist** is the dominant element: 0/4 done, "Estás a 4 pasos de tu primera venta."
